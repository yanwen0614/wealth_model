# 下一次实验前的必读说明

**写于 2026-10-30，依据本轮工程整理中实际发生的事故与教训。**
**用途：下一次开始任何训练/回测/研究实验前，先按本文自查。每一条都对应一次真实损失或一次真实返工。**

---

## 一、本轮整理暴露的四个真实事故

### 事故 1：未提交的研究代码随工作树被删，18 个文件凭空消失

**发生了什么**：退役工作树时按"直接删除不存档"处理，但树里有 18 个从未 `git add` 的研究源文件。删树即删文件，主仓库里零副本。

**当时本可避免的三件事**：
- 删之前没区分"已合并进主区的"和"只存在于工作树未提交的"；
- 删之前没跑 `git status --porcelain --untracked-files=all` 逐条过一遍未跟踪文件；
- 按"已合并"的假设处理了整棵树。

**救回来的方式（不可依赖）**：从 opencode 会话数据库 `~/.local/share/opencode/opencode.db` 里，用历史 `read` 快照 + `apply_patch` 补丁重放，逐字节还原。**这是运气，不是流程**——如果当时没人读过那些文件全文，就真没了。

**规则**：删除任何包含未提交内容的目录前，必须先把未跟踪文件单独列清单并归档；`git status` 里每一个 `??` 都要有人签字确认"可以丢"。

### 事故 2：一个模块从未入库，但已提交的代码在 import 它

**发生了什么**：`quantity_rules.py` 一直是未跟踪状态，而 `staged_candidate_runner.py`、`staged_production_inputs.py` 和两个测试已经在 import 它。工作区能跑，是因为那两个文件恰好还在磁盘上。任何人从 HEAD 干净检出，直接 `ModuleNotFoundError`。

**规则**：提交前，对新增的 `import` 目标逐个确认 `git ls-files --error-unmatch` 通过。**"我本地能跑"不是证据，"干净检出能跑"才是。**

### 事故 3：连续三次提交把 CI 打红，因为没验证真口径

**发生了什么**：以为 `_check_signals.py` 的 lint 告警是"既有问题"，实际上该文件未被跟踪、CI 全新 checkout 里根本不存在。按当时的判断提交，会让 CI 变红。

**规则**：判断"是不是既有问题"不能看本地工作区，要看 CI 的真实口径（已跟踪文件 + 配置里的 exclude）。本地脏文件造成的告警既不能算既有问题，也不能算自己引入的问题，它是第三种状态——**必须先分类再决定修不修**。

### 事故 4：给文件的指纹，指向从未落盘的字节

**发生了什么**：`SOURCE_HASHES_FINAL.json` 里有 4 个文件的 pin，用全历史 177 个提交 × 3 种行尾变体穷举，零命中。也就是说记录时哈希的对象从未写进磁盘。

**规则**：**pin 必须在文件落盘之后计算，且从磁盘重新读取后再算一遍确认**。不能在内存里算完就记下来。

## 二、四条硬性操作规范

### 规范 1：证据与代码同生命周期

| 类型 | 必须满足 |
|---|---|
| 代码 | 提交进 git；提交前验证干净检出可 import |
| 冻结输入 | 落盘 + 算哈希 + 哈希本身也落盘 + 定期校验 |
| 运行产物（账本/报告） | 至少一份在 git 之外的第二物理盘 |
| 生成它们的命令 | 写进仓库，且命令里不含绝对路径 |

### 规范 2：任何"删除"都要先能重建

删之前问三个问题：
1. 这是唯一副本吗？
2. 能从 git / 备份 / 会话记录重建吗？
3. 重建后能验证一致吗（哈希比对）？

三个问题有一个答不上来，就不许删。**"用户说直接删"不等于"这个文件可以丢"**——指令针对的是已合并的部分，未提交部分需要单独确认。

### 规范 3：绝对路径是复现的敌人

本轮实测：58 处绝对路径分布在 31 个文件；4812 个冻结产物的键全是绝对路径。结果就是换机器、换目录、换盘符全部失效。

- 代码里不许出现 `C:/Users/<name>/...`、`D:/code/...`；
- 冻结产物里的绝对路径**不许改写**（改了就改身份），改用 sidecar 映射表；
- 关键路径通过环境变量或配置文件注入，且提供默认探测。

### 规范 4：不许用"现在的代码"冒充"当初的运行"

本轮最关键的认知：`git merge` 能让代码齐备，但不能复原运行现场。缺的有五类——没落盘的字节、写死的路径、删掉的目录、没签的名、旧 schema。

**因此，要证明历史结论，必须当时就记录**：
- 运行器（runner）自身源码的哈希，不只是它依赖的库；
- 完整的 import 闭包（本轮实测有 5 个实际执行的模块完全不在任何 pin 清单里）；
- 运行环境的版本（torch/CUDA/线程数）；
- 输入清单的哈希。

**这些没记，事后永远补不回来。** 补出来的只能是"新建一个长得很像的东西"。

## 三、每次实验开跑前的检查清单

打印出来贴在手边。

### 开工前

- [ ] 实验目录在 git 仓库内，或已明确声明为"不入库证据"并做了异盘备份
- [ ] 代码全部已提交，`git status` 干净（未提交的代码不许开跑）
- [ ] 运行命令写进仓库，不含绝对路径
- [ ] 冻结输入的哈希已生成且已落盘
- [ ] 运行器自身源码哈希已记录（含完整 import 闭包）
- [ ] 环境版本已记录（python/torch/cuda/依赖锁文件）
- [ ] 通过/否决标准**已书面写死**，且在跑之前

### 跑的时候

- [ ] 长任务用 tmux（不要放在工具调用的前台子进程里）
- [ ] 每完成一个阶段就落盘中间结果，不要等全部结束
- [ ] 出现不确定的数据（如碎股、未知登记日）时 fail-closed，不许猜
- [ ] 中断要记录原因，不要静默重试

### 跑完之后

- [ ] 产物做一次自校验（账本恒等式：nav = cash + 持仓市值 + 应收）
- [ ] 产物的哈希与位置写进报告
- [ ] 明确标注状态：完整 / 部分 / 不可评价（不许模糊表述）
- [ ] 若结论涉及收益，必须有同期基准、且基准口径写清楚
- [ ] 并列的所有候选都报，**不许只报最好的那个**

## 四、本轮整理的其他具体教训

### 关于测试

1. **skip 不等于 pass**。本轮 40 个用例里 33 个 skip，原因是"依赖已删除的东西"。这些测试的输出是绿色的，但什么都没验证。CI 应该打印 skip 数量，并对异常 skip 设阈值告警。
2. **"全绿"要先定义边界**。本轮 CI 只跑 58 项，本地全量 982 项里有 12 项红。"CI 全绿"和"有 12 项红"同时成立，说"全绿"时不说明边界就是误导。
3. **删除代码后要确认 0 新增失败**，而不是"失败了但看起来跟以前一样"。本轮用逐行比对方能确认。

### 关于数据

4. **缺口的成因要分类，不要笼统说"数据不全"**。本轮查明：停牌/上市前/退市后的缺口在源头本来就没有行情，**补出来就是伪造**；能补的只是标签。真正能补数据的只有一类——200 只退市股整只没落盘（取数函数只取 active）。
5. **不要把人工维护的数据当成源头数据**。暂停上市约 4 万条是人工补的 13 只，SDK 根本不提供；换标的必须重新做官方公告取证。
6. **有标记不等于有数据**。"源头有停牌标记"回答的是"为什么缺"，"缺的值是多少"仍是空的。

### 关于文档

7. **结论文档里每个数字都要有出处**，且出处不能是另一个二手文档。本轮发现文档之间层层转述，最后数字漂移了。
8. **改写数字时要同时改所有相关处**。本轮出现过同一份文档里同一组指纹给了两套数（7/7/1 和 10/1/4），读者无法判断以哪套为准。
9. **状态词要定义清楚**：没跑完（INCOMPLETE）、主动拒绝（NOT_EVALUABLE）、证据不全（未验收）是三种不同的事，不能混用。

### 关于并行

10. **一个工作区同一时间只允许一个编码代理改动**。本轮并行派了多个代理，靠"文件范围物理隔离"才没出事——每个代理只能改明确列出的文件，禁止 `git add -A`。
11. **并发提交会互相干扰**。多个代理同时提交时，后提交的会基于前者的结果，容易出现"文档里写的数字是旧的那一版"。本轮出现了三轮文档订正，就是因为数字在并行过程中变了。
12. **派出去的代理要给它明确的"停止点"**。比如"先报告、等我确认后再提交"，否则它会一路跑到底，包括你不想要的提交。

### 关于判断

13. **不要把"未完成"当成"证伪"**。W1 是中断（没有数字），不是亏损；W2 是有完整账本但资格不全，不是算错了。三种状态必须分开表述。
14. **不要把"部分通过"当"通过"**。限定性结论必须写明限制条件（例如"限指标复现，不含训练重跑"）。
15. **不要事后择优**。本轮四个策略里 B1 最好，但只报 B1 属于违规；四个必须并列。

## 五、一句话总纲

**没有记录的东西等于不存在。**
代码要记录（提交）、输入要记录（哈希）、运行要记录（runner 哈希+环境）、结论要记录（状态+边界+出处）。

本轮所有"不可复现"和"永久丢失"的问题，根因都可以归到这一句上。
